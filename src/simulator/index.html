muir-sim simulates both on your own computer, as two executables: quux for QUUX, and cadr for MIT’s machine as built, from MIT’s schematics of its boards.

01 / WHAT IT IS

The machines,
in software.

muir-sim runs the CADR’s software by simulating its hardware, not by reimplementing Lisp, and boots the last release of the Lisp Machine software MIT made, restored from tapes the MIT Tapes of Tech Square project recovered. QUUX, beside it, runs muir-sys’s updated system. muir-sim is written in Rust and has no crate dependencies.

What the two machines are, their processors, buses and boards, is on their own pages: the CADR and QUUX.

02 / WHAT MUIR-SIM DOES

Three engines.
One machine, three depths.

muir-sim has no Lisp of its own. It simulates the CADR from MIT’s own schematics of its boards, and MIT’s software runs on it unchanged: the microcode, the Lisp system, and MIT’s debugger for the machine. QUUX runs muir-sys’s microcode and system.

The CADR’s processor carries out each instruction as a series of small steps, written in microcode; one step is a microcycle, and the real machine did about 6.9 million of them a second. muir-sim simulates it at three levels of detail, and all three agree at the end of every microcycle, so the fast ones can be checked against the slow one. QUUX runs on micro and rtl; chip is the CADR’s alone.

01 — MICROTHE FAST ONE

60 M/s

about 9x the machine

What each microcycle does, and nothing about when. The quickest way to boot the system and use it.

--micro
02 — RTLTHE EVERYDAY ONE

16 M/s

about 2x the machine, flat out

What each microcycle does and when: waits on the buses, timeouts, the debug cable. It could run twice the machine’s speed, but by default it is held to the machine’s own, so the machine’s clock keeps the day’s time; --no-pace lets it run flat out.

--rtl
03 — CHIPEVERY CHIP

1,400/s

about 1/5,000 of the machine

MIT’s schematics of every board, simulated part by part and wire by wire. Far too slow to use, and the reference the other two are checked against.

--chip

The worst case, with everything fitted: the color TV on every engine, and on chip MIT’s disk controller with its multiplexor as well, every board a netlist. Rates are flat out, with no pacing, from cargo run --release --example benchmark -- --everything on one core of an Apple M4, rounded down; without the second display board chip runs about 2,000/s and the other two the same. The machine’s own microcycle is 145 ns, so the hardware runs 6.9 M of them a second. What each engine computes on the way to the next one is in the manual.

Build it.

The Rust toolchain.

Install rustup, then open a new shell so cargo is on the path.

02

Clone and build.

git clone https://github.com/metebalci/muir-sim
cd muir-sim
cargo build --release

That builds quux and cadr. cargo test beside it is optional, and a fresh clone passes with nothing fetched.

03

QUUX’s system.

tools/fetch-system-for-quux.sh

QUUX is the CADR evolved, and quux runs it, with its own boot PROM, the video controller and block-disk. It needs muir-sys’s updated microcode and system on a raw image or a VHD with a GPT partition table: MIT’s own will not run on it. The script fetches QUUX’s current release, System 2000, and checks every file against its SHA-256 sum. It puts the machine’s disk in vendor/run/ and makes the machine’s host folder beside it: QUUX reads its files from there through a device of its own, so it needs no file server. muir-sys’s building notes say how the system is built.

04

Run it.

target/release/quux --micro --disk-pack vendor/run/release-2000-disk.vhd \
    --file-root vendor/run/release-2000-root

quux on the fast engine, micro; without --micro it runs rtl, at the machine’s own speed. Its microcycle is 40 ns, always, and on the rtl engine its cache and main memory are timed as the slower FPGA board’s. It prints where its screen is: point any VNC viewer there. It boots to a Lisp Listener, System 2000; (login "LISPM" "HOST" t) logs in.

QUUX is still being developed: its hardware revisions, microcode and system change, and a later QUUX need not run today’s bands or microcode.

03

MIT’s last release.

tools/fetch-system-100-for-cadr.sh

System 100, the CADR’s: a disk pack, a file that stands in for the machine’s disk and holds its microcode and a band, the saved Lisp world it boots into; and the system’s sources. Neither is part of muir-sim: the script fetches them and checks every file against its SHA-256 sum. muir-sys also evolves a system for the CADR, on the CADR’s own line of releases: tools/fetch-system-for-cadr.sh fetches its current one, and its release notes give the ozd and cadr commands.

04

Run it.

target/release/cadr --disk-pack vendor/run/disk-sys-100-0.img \
    --chaos-address 3050 --chaos-udp 42043 --chaos-udp-peer 3060@127.0.0.1:42042

cadr on the everyday engine, rtl, booting System 100 off the pack. The Chaosnet is the machine’s network, and this band expects to be machine 3050 on it and to ask host 3060 for the date and for its files. It prints where its screen is: point any VNC viewer there.

The file and time host at 3060 is not the CADR. A CADR had no such server in it, so it is a program of its own on the network — ozd. A band that reaches no host boots all the same, but stops to ask for the date: Super-B at the debugger, then the date and time it asks for and y, finish it.

05 / THE MACHINE IN MUIR-SIM

A model
of every board.

Every box is a board of the CADR, simulated from MIT’s schematics on chip and as a model of the board on the other two engines; this is how muir-sim puts them together. The boards, the buses and the seven netlists are on the CADR’s page.

Every board a netlist at once, and MIT’s system cold-booted through them — twice. Each run is more than 60 hours of gate-level simulation: 2 days 14 hours and 301 million microcycles on 12 September 2026, and 2 days 21 hours and 306 million with the disk multiplexor fitted as well on 15 September 2026. The machine’s own report at the end of each, printed in its who-line, was Cold-booted. Both runs are in the manual.

06 / THE ACCEPTANCE TEST

Two machines,
one debugging
the other.

A real CADR could be debugged from another CADR. A cable joined the two machines’ bus interfaces, and a program on one could stop the other, step it and read out its insides, even when its own software had crashed. That program is CC, MIT’s console debugger for the machine.

muir-sim’s acceptance test is exactly that. Two simulated machines are joined by the simulated debug cable. The first boots System 100, logs in and loads CC over the network; CC then halts the second machine and reads back where it had got to. It passes only if the processor, memory, disk, network, file loading and both ends of the debug cable all behave as MIT built them.
