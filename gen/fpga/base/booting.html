How a board comes up

Two sequences, one for each way a board here starts: a Zynq board from its own card, and the same board from a TFTP server while it is being worked on.

The two Zynq boards come up the same way as each other, so one drawing serves both. Where they differ, the drawing says so in a label.

A Zynq board on its own

This is how a board boots for anybody who is not this project. Everything it needs is on the microSD card: the loader, the CADR's bitstream, Linux with its root filesystem, and the disk packs. No network is used and none is needed.

Three files keep fixed names at the root of the card's boot partition, because those names are not ours to move. The boot ROM reads BOOT.BIN there and nowhere else, that first stage asks for u-boot.img by name beside it, and uEnv.txt is imported before any board name is known. The four files the loader goes on to read sit in a folder named for the board, which is the same name the server's directory for that board carries.

A Zynq board for development

This project's own boards take the same five files from a TFTP server instead. A change to any of them is then a copy and a reset, and the card is never rewritten. The card's uEnv.txt is what decides between the two paths, by whether it names a server, and one U-Boot environment carries both.

One server here serves more than one board, and every board's five files carry the same five names, so each board's set sits in a directory named for the board. A flat root would hand a board a bitstream for another part, which configures nothing and says nothing about why. The network path does not fall back to the card's own copies: booting stale files silently is the thing this project decided against.
